# The draft skin builder boundary

Design for the standalone application · 23 November 2026

**Give the app one replaceable operation that constructs the draft surface.** It starts from a revisioned snapshot of the contributing anatomy and returns one owned surface in project coordinates. The app binds that surface to the anatomy and publishes it as the envelope. Both **Build Envelope** and **Build Skin** go through this operation. A future builder can use a completely different construction algorithm.

The mapping below records the pre-integration baseline. The [rollout decisions](#experimental-rollout-decisions) describe the implemented selector and adapters.

## Contract for a replacement

Only two operations need to vary at the app boundary.

| Operation | Input | Result |
| --- | --- | --- |
| **Describe required inputs** | Authored document, selected implementation and its settings. Reads metadata only so the app can use it for scheduling and availability. | Required source roles, revision dependencies, execution requirements and supported route/settings combinations. Missing capabilities give a specific reason. |
| **Build the surface** | Immutable resolved source snapshot, selected settings, run-scoped resource access and cancellation. The adapter receives each required surface with its identity, coordinate convention and revision. | One owned native mesh in project space, actual builder ID/revision and its diagnostics and warnings, or a failure with the source/stage that failed. |

The shared envelope stage assembles the binding resource and returns the existing `ComputedStage(mesh, data)`. A worker that runs out of process must transfer geometry into app-owned memory before scratch cleanup. Validate finite coordinates, index bounds and usable connectivity before handing a mesh to native consumers. Preserve the existing quality-warning semantics and the distinction between a measured zero and an unavailable check. Keep legacy voxel resolution and AVBD solver receipts as method-specific metadata. Store binding owners against the app's source table even when the solver processes sources in a different order. Move the shared source-metadata helper out of the legacy evaluator when extracting it, since topology imports it too. [Asset format](../../src/anthroforge/application/skin_assets.py) · [Quality reporting](../../src/anthroforge/native/skin_diagnostics.py)

**Switching.** Register implementations at the application's composition root. Persist the desired builder ID and method settings in the document and record the actual producer and implementation revision on each new draft. Old projects without a selection resolve to today's field builder and retain their saved assets. A selection change is undoable, marks construction stale and takes effect on an explicit build. Ordinary updates continue using the accepted deformation reference. An unavailable selected builder blocks that build with a reason, while the previous accepted skin remains usable. A standalone topology rebuild uses the accepted draft's provenance. Desktop, CLI and a frozen export that needs a rebuild must resolve the same document selection. The experiment's per-subtree Follow, Limb and Region choices belong **inside** its builder. ## Implementation order and acceptance

1. **Extract the existing field builder first.** Route both commands through it. On the same app document, compare mesh positions/connectivity, binding arrays, source ordering, quality and warnings before and after. Preserve legacy asset readability. Any intentional new producer metadata must be compared separately from content hashes that include metadata.
2. **Connect a second implementation through the same interface.** Export a real document snapshot and compare its source slots, transforms, recipe and resulting draft with the qualified capture. Exercise a mirrored instance, bone-only construction, VCP displacement and an unsupported route. A missing tool, invalid tissue pair, cancelled run or superseded selection must leave the last accepted draft usable. A late job must never publish over a newer selection.
3. **Follow the result through real app consumers.** Build quad topology and reference, check geometry and the open hand passages before and after retopology, then exercise live update, fit, frozen export, undo and save/reopen. Confirm a backend switch influences the subsequent construction and leaves ordinary fixed-topology updates on their recorded reference.
4. **Measure the interface cost separately from the solver.** Time capture/staging, native process startup, solve, mesh import, binding and publication. Record peak memory and scratch. Packing input and importing output should each scan the transferred buffers once. Owner-to-slot lookup is indexed. Keep the legacy scene shared across construction and binding. The experimental sequence already rewrites cumulative active colliders across stages, so its total staged bytes can exceed the final anatomy size. Compare against each implementation's direct run before attributing cost to this interface.

A new builder should plug in through its requirements, adapter, settings and registration. The scheduler, topology, deformation and export should continue consuming the same accepted stage. This is the practical substitutability test.

## Using the experimental builder

In the development checkout the adapter launches the existing AVBD worker with that checkout’s Python environment and compiled native tools. To use a separately built worker, set `ANTHROFORGE_AVBD_RUNTIME` to its worktree root before launching the desktop app. A missing runtime produces a failed job with a diagnostic. Launch this checkout with [tools/run.ps1](../../tools/run.ps1). The installer packaging and interactive editor for anatomical routes remain separate work.

The default plan is `{}`. An imported plan can override `bones`, `muscles` and `normalization` independently. Each supplied list must contain every active source of that kind exactly once. Use document owner IDs, or the app's mirror instance IDs. Keep the names and filesystem paths of experimental capture assets out of the plan. For example, a project with one SCP and one tissue might import:

```json
{
  "bones": [{"id": "actual-project-scp-id", "route": "follow"}],
  "muscles": [{"id": "actual-project-tissue-id", "frames": 63}]
}
```

Bone routes are ordered Follow, optional Limb, then optional Region after a limb. Limb rows supply `settings`; Region rows supply `joint` as an origin, an axis and a normalized station. The [qualified construction recipe](../../tests/fixtures/draft_skin/recipe.json) illustrates these parameters. To build an app plan from it keep identity, route and route parameters for bones and identity and frame budget for tissues. Substitute the current project's IDs. Without an explicit normalization the adapter uses the root bounds center and diagonal. An explicit normalization is the four numbers `[cx, cy, cz, scale]` in project space.

## SCP properties, traversal and checkpoint agreement

Field remains the default on new and existing projects. AVBD is opt-in. Author Follow SCP or Fill Region in SCP properties, or inherit from the closest explicit ancestor. The root defaults to Follow. An explicit Fill starts a region. Follow ends that region on its branch. Empty organizational SCPs participate in inheritance. Every limb belongs to its declaring child SCP. Nested limbs have independent rest spheres. Deleting a limb preserves descendant declarations and route overrides. Reparenting preserves authored settings and resolves inheritance and attachment again.

Version 3 derives the limb opening from the parent attachment and stores material as lengths per triangle. The material radius changes the target length ratio for new faces relative to the automatic child attachment radius. The boundary radius independently controls the seed opening. Historical spherical placement decisions below describe prior versions. See DSB-RF5 for the version 3 upgrade checks.

Walk the authored SCP tree depth first, parent before child, siblings in saved order. Build consecutive changes on the incoming accepted shell. Only a matching complete prefix is eligible for checkpoint reuse, including warm solver state. Independent branch reuse and parallelism require separate qualification. After all SCPs, apply ready tissue VCPs in saved object order using their base and final surfaces. A new last VCP can resume the single combined checkpoint only when the entire prior input prefix still matches. Changes to an earlier base, inflation, stack result, order or membership replay the current VCPs from the skeletal checkpoint.

Committed construction changes schedule background draft catch-up. Posing uses fixed topology. Keep the accepted draft visible during work and after failure or cancellation. Show partial progress explicitly if no draft has ever completed. Topology and reference operations remain explicit. The ordinary project saves settings and accepted skin without construction checkpoints. Save As also offers `.anthroforgex`, storing one checkpoint per SCP and one completed combined VCP checkpoint. Save retains the chosen format. Checkpoint compatibility includes source inputs, order, solver and builder revision. A temporary VCP prefix can support in-session retry.

### Fixed-boundary spherical UV qualification

DSB-UV1 (implementation choice). Measure both planar and spherical signed orientation after equilateral placement. On a reversed physical triangle try moving only an incident unpinned vertex inside the intersection of its neighboring planar and spherical orientation constraints. Preserve every original setting, chart boundary, hole, physical face and solver admission check. A forward stereographic lift gives a quadratic signed side test in UV. A bounded linear lower estimate plus independent post-check allows safe candidate selection. Build adjacency once per affected patch, O(F+V) storage. For a vertex of valence d sort at most 2d+4 half-planes in O(d log d) per fixed radius and margin trial. A successful move must reduce the number of inverted faces without invalidating any incident triangle. This is a local repair with an explicitly checked domain, not a claim of universal fixed-pin feasibility. Verify the saved full project, reference controls, impossible fixed constraints and unmodified valid inputs.
